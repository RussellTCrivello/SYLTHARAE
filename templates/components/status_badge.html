{# component: status_badge purpose: One way to show a status word, so the same state is not green on one page and grey on the next. An application status is looked up in the vocabulary - `core/frontend/status_vocabulary.py` - which maps it to one of a few presentation states; the component only turns that state into classes. states: success, warning, error, unavailable, archived presentation_states: success, warning, danger, info, progress, neutral, muted classes: badge, bg-secondary, bg-success, bg-warning, bg-danger, bg-info, bg-primary, text-dark, ms-2, bg-success-subtle, text-success-emphasis, bg-light, border notes: Two callers, one owner. Pass `status=` for anything the application calls a status (`status_badge(status='COMPLETED_WITH_WARNINGS')`) and the vocabulary decides the state and the words. Pass `label` and `tone` only for a chip that is not an application status - a count, a method, an id - because a presentation state chosen at the call site is exactly the drift this component exists to stop. A status nobody has heard of renders neutral, in its own words, marked `data-status-known="false"` rather than being given a meaning. #} {# Usage: {% from 'components/status_badge.html' import status_badge %} {{ status_badge(job.state, tone='success') }} Tones: neutral, info, primary, success, warning, danger, muted. #} {#- Presentation state -> stylesheet classes.
